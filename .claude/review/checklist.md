# claude-code-guard の観点

このリポジトリに固有の観点。消した ID は使い回さない。各項目には観点と確かめ方だけを書き、経緯は書かない。共通の観点と言語ごとの観点は `~/.claude/skills/adversarial-review/checklists/` にある。

## ガードの前処理と判定

### N-1 前処理の除外が検査を消さない
- 観点: コメント・引用符・ヒアドキュメントなどを除く前処理が、検査してほしい部分 (実行される文字列) まで消していないか
- 確かめ方: 除外の対象に見えて実際には実行される入力 (`$(...)`、`bash -c '...'`、`eval`) を、除外の前後に置いて試す
- データとして外す値 (`-m "..."`、`--body`、引用符の無い heredoc の本文) の中に `$(...)` やバッククォートを入れ、機密パスやハーネスへの書き込みを置いた入力を試す。外してよいのは、展開が起きない形 (シングルクォート、引用符付きの heredoc) だけ
- コメントを外す前処理 (`--`、`#`、`/* */`) は、文字列の中の同じ記号で後ろの文まで消さないか。`SELECT '--'; DELETE ...`、`SELECT '/*'; DELETE ...; SELECT '*/'` の形で試す
- heredoc や文字列の中の `$(` は、複数行にまたがる形と、引用符の中の `)` を含む形 (`$(cat ")" x)`) でも試す
- フラグの名前でデータとして外す処理 (`-m`、`--title`) が、そのフラグをメッセージとして扱うコマンド (git commit、gh pr など) に絞られているか。値を取らない同じ名前のフラグ (`sort -m`、`less -m`) の後ろに読み出しを置いて試す

### N-2 語の再構成とデータの除去を別の前処理に分ける
- 観点: 語を組み立て直す処理 (引用符の連結、変数展開の復元) と、データを外す処理を 1 つにまとめていないか。まとめると、片方の都合でもう片方の検査が消える
- 確かめ方: 引用符で語を割った入力 (`g"i"t push`) と、データ部に命令らしい文字列を入れた入力を、別々に試す

### N-3 例外の判定が本体と同じ対象を見る
- 観点: 例外 (初回 push の許可、守るブランチ以外など) の判定が、本体の判定と同じ「対象のリポジトリ・ブランチ」の取り出しを共有しているか。別の取り出しだと、判定と例外が別のリポジトリを見る
- 確かめ方: `-C <dir>`、`--git-dir`、`cd x && git push` で対象を変えた入力で、本体と例外が同じ対象を見るかを確かめる
- 対象を変える入力に次も足す: `GIT_DIR=` / `GIT_WORK_TREE=` の接頭辞、`cd -P x`、`pushd` と `popd`、終わったサブシェルの中の `cd` (`(cd x && make) && git push`)、引用符で包んだ `'HEAD'` / `"@"`、小文字の `head`、`refs/` を省いた `heads/main`、`:` だけやワイルドカードの refspec
- ハーネスの書き込みの判定でも、`cd x && <書き込み>` の相対パスを試す。`(cd x && ...)`、`{ cd x; ...; }`、`cd -- x`、グロブの移り先、`pushd` だけ (cd を含まない) の形、空白なしのリダイレクト (`x>y`)、`./` 付きの相対パス、`--opt=value` も試す
- 文字列や別のコマンドの中の `cd` / `GIT_DIR=` (`echo "a; cd /tmp" && git push`、`GIT_DIR=x true; git push`) を、push の場所として誤って採らないか。失敗しうる cd (`cd x || true; git push`、`cd x; git push`) では元の場所も見るか

### N-15 コマンドの語の直後の区切り
- 観点: コマンドの位置の判定で、語の直後に空白なしで `;`、`&&`、`|`、`)` が続く形と、`{ }` や `( )` で囲んだ形を見ているか
- 確かめ方: `git push;`、`git push&&x`、`git push|cat`、`(git push)`、`{ git push; }` を試す
- コマンド置換の中の語では、語の直後が `<` / `>` の形 (`$(rev<<<x)`、`$(printf>/dev/stdout x)`) と、オプションを分けた形 (`echo -n -e`) も試す
- コマンド名を大文字や混在で書いた形 (`PRINTF`、`XARGS`) も試す。macOS の既定のボリュームでは、PATH の探索が大文字小文字を区別しないので動く

### N-4 例外条件が代理の事実だけで決まらない
- 観点: 例外が「リモートが空に見える」「ファイルが無い」など、間接の事実だけで通っていないか。確かめられないとき (通信の失敗、タイムアウト) は block か ask に倒れるか
- 確かめ方: 事実の確認を失敗させた入力 (通信の遮断、存在しないリモート) で、判定が許可に倒れないことを試す

## 終了コードと資源

### N-5 `$? >> 8` がシグナル死を成功にしない
- 観点: perl の `system` や `wait` の戻り値を `>> 8` で終了コードにしたとき、シグナルで死んだ子 (下位 7 ビットが非 0、上位が 0) が 0 = 成功に見えないか
- 確かめ方: 子を `kill -9` で落としたときの判定が、失敗 (block か ask) になるかを試す

### N-6 上限を保存するファイルの書き込み失敗
- 観点: 回数や時間の上限を状態ファイルに保存するとき、書き込みの失敗 (読み取り専用、権限、容量) で上限が効かなくなり、無限に回らないか
- 確かめ方: 状態ファイルを書けない場所に向けて実行し、上限を超えて回らないことを確かめる

### N-7 時間切れで TERM を無視する子と背景プロセス
- 観点: タイムアウトで子を止めるとき、TERM を無視する子や、背景に残るプロセスが残らないか。待ちが無限に延びないか
- 確かめ方: TERM を無視するコマンド (`trap '' TERM; sleep 100`) と背景起動 (`sleep 100 &`) を検証ループに入れ、時間内に戻り、プロセスが残らないことを見る

## 検出器と文書

### N-8 補助の検出器の網羅
- 観点: 「語が割られているか」を調べる検出器が、本体の判定が読む位置と同じ集合 (コマンド名そのもの、パス付き、バッククォートの直後、引数の語全体が展開のとき、行継続の位置) を見ているか
- 確かめ方: 「引用符・展開・継続」と「コマンド名・サブコマンド・引数」の表を作り、全マスをテストにする。行に「`bash -c` / `eval` の中」、列に「引用符の入れ子 (`"git "push" ..."`、`\"push\"`)、行継続」を足す。`$'..'` / `$".."` をコマンド名の行に足す
- 止めすぎの側も確かめる: コマンド名・サブコマンドの位置以外の語 (`grep "git"`、`echo "git"`) で ask が出ないかを見る

### N-9 補助の検出器の失敗
- 観点: 外部スクリプトの出力が空であることを「問題なし」と読んでいないか。終了コードと欠落 (ファイルが無い、構文エラー) で ask か block に倒れるか
- 確かめ方: 検出器のファイルを壊した状態で本体を流し、判定が ask になるかを見る

### N-10 README と Known limits の記載が検出器のテストに対応している
- 観点: 「〜は確認に回す」と書いた形が、テストに 1 ケースずつあるか。書いた形に対応するテストが無いものは、限界として書く
- 確かめ方: README の記載ごとに、対応する ASK のテストを並べる

## 判定の網羅

### N-11 パスの前に来る文字
- 観点: 機密パスや守るパスの判定が前提にする「直前の文字」の集合に、リダイレクトの `<` と `>`、`rev:path` の `:`、`--opt=` の `=` が入っているか。名前を組み立てるグロブ (`.en?`) とブレース展開 (`.e{n,x}v`) を見ているか。パスの書き方の揺れ (`//`、`/./`、`dir/..`) を畳んでから比べているか
- 確かめ方: 各パターンを `<x`、`HEAD:x`、`--file=x`、`x` を含むグロブ、`~//x`、`~/a/../x` の形で試す

### N-12 同じ効果に届く別の経路
- 観点: 守る規則が、同じ効果を持つすべての経路を見ているか。設定なら、キーの指定、設定ファイルへの直接の書き込み (グローバルと XDG の置き場所)、置き場所を変える環境変数 (`HOME`、`XDG_CONFIG_HOME`)、ツールの新しい書式 (`git config set/unset/remove-section`)、セクションごとの削除。書き込みなら、リダイレクトと `sed -i` のほかに `perl -i`、`dd of=`、`curl -o`、`git checkout <rev> -- <path>`。実行なら、フルパスや `env` を付けたコマンド名と、別のインタプリタ。CLI で止める操作は、MCP のツール (ブランチに直接コミットするものを含む) でも止まるか
- 確かめ方: 経路ごとに 1 ケースずつ試す
- 実行時に引数を足す経路 (`xargs`、`parallel`、`find -exec {}`、`while read`) と、指定したブランチにコミットする MCP のツール (`delete_file`、`create_file` など。`branch` が空で `ref` に値がある形も) を、経路ごとに試す
- ブランチに書く MCP のツールは、`branch` / `ref` 以外のキー (`refspec` の `HEAD:main` や `+main`)、引数が無く今のブランチに書く形 (`git_push {}`)、入れ子の中のキーも試す。同じ名前で引数がある場合と無い場合を流し、無いほうが緩くなっていないかを見る

### N-13 判定を広げたときの巻き込み
- 観点: 判定の対象 (直前の文字、書き込みの手段、語の位置) を広げたとき、既存の許可 (`terraform -var-file=x.tfvars`、`chmod +x` だけ、`curl | jq`、`git checkout <branch>`) を巻き込んでいないか
- 確かめ方: 広げた規則ごとに、既存のテストの ALLOW と、よく使うコマンド (ビルド、テスト、グロブ付きの `ls` / `cp` / `rm`) を流し、止まらないことを見る
- 範囲を絞った・書き直した規則 (パイプの中間の段など) では、以前 block だった入力 (`curl | grep | sh`) が通らなくなっていないかを、main 版と同じ入力を流して比べる
- 名前の語で判定する規則を足したら、その語を含む読み取り系の実在の名前 (`get_status_push`、`get_workflow_run`、`get_post`) を流して、止めすぎが出ないかを見る
- 名前の見本と照らす規則は、よくある拡張子 (`*.txt`、`*.json`) と、`[[ == ]]` や `case` のパターンで試す

### N-14 検証ループの前提が崩れたとき
- 観点: git の外やコミットが無いリポジトリで、「変わったか」の判定が仕様どおりか (走りすぎ・飛ばしすぎ)
- 確かめ方: git でないディレクトリと、コミットが無いリポジトリで、変更なしの Stop と、ステージだけ変えた Stop を試す。git の外では、mtime の変わらない変更 (mv) と削除も試す

### N-16 利用者の承認を置く仕組み
- 観点: 利用者が見て承認した内容と、承認が有効になる範囲が一致しているか。承認を書く側 (利用者の端末) と読む側 (フック) で、置き場所が同じになるか
- 確かめ方: 上限を超える長さのファイルと、`\r` や ANSI エスケープを含むファイルで承認し、見せた範囲と有効になる範囲を比べる。書き手と読み手を、実運用と同じ環境変数の有無 (`CLAUDE_PLUGIN_DATA` あり / なし) で別々に起動する。テストが環境変数を明示して両者を揃えていないかを見る
- シンボリックリンクと、そのファイルが呼ぶ別のファイルが承認の外で変わらないか。通知は同じ内容につき 1 回で、内容が変わったら再び出るか (黙ってスキップすると、通ったように見える)

### N-17 承認の記録・承認のスクリプトへの経路
- 観点: 承認の記録 (`verify-trust/`) に届く経路を、Bash とファイルのツールの両方で止めているか。承認のスクリプトを実行する形を、`env` / `exec` / `nohup` / `time` / `xargs` / `command`、`{ }`、絶対パスのインタプリタ、引用符で割った名前、グロブ、コピーしてから実行、で見落とさないか
- 確かめ方: 上の形を ASK のテストにする。`$CLAUDE_PLUGIN_DATA` 経由、`cd` してからの相対パス、`$HOME` 配下の置き場の直接指定でも書き込みが止まるか試す。実行時に組み立てた名前は通るので、README と spec に「補助」と書いてあるかを見る

### N-18 検出の形を足したとき
- 観点: 足した形に、同じ文の別の書き方 (括弧で始まるサブクエリ、別名、語順の違い) を当てても検出できるか。同じ入力を、名前で経路が分かれる 2 種類のツール (SQL を受けるツールと受けないツール) に流して、判定が揃うか
- 確かめ方: 形ごとに別の書き方を 1 件ずつ ASK のテストにする。`mcp__db__query` と `mcp__db__run` の両方に同じ文を流す

### N-19 cwd を読む判定
- 観点: `cd` や `pushd` で移った先を、新しい判定が見ているか。実展開のように、cwd の実ファイルを読む判定は、cwd 固定のままになりやすい
- 確かめ方: 機密のあるディレクトリへ `cd` してから打つ形 (`cd d && cat *`、`bash -c "cd d; cat *"`) を試し、見ない場合は spec と CHANGELOG の Known limits に書いてあるかを見る

### N-20 設定値の検証
- 観点: 使えない文字を含む設定値を、黙って捨てていないか。捨てたことが利用者に分かるか
- 確かめ方: 使えない文字を混ぜた値 (`v[0-9]*`、`hotfix-?`) を渡し、無視されることが説明文に書いてあるかを見る

### N-21 判定の対象を「書き込み先だけ」に狭めるとき
- 観点: 引数の位置で宛先を決める判定 (最後の引数など) が、値を取るオプション (`--exclude x`、`-m 755`)、終端記号 (`find -exec ... +`)、エスケープした空白 (`a\ b`)、引用符の中の `#` で宛先を取り違えないか。宛先に狭めたことで、リンクの向き先 (`ln -s 保護パス /tmp/l` の後にリンクへ書く) のような間接の書き込みが見えなくならないか。読み切れないときの既定が、狭める前の広い判定になっているか
- 確かめ方: 変更前の版と同じ入力の一覧を流して終了コードを比べ、block から通過に変わった入力をすべて挙げて理由を説明する。宛先の後ろに値を取るオプションを置いた形、`+` で終わる `find -exec`、バックスラッシュと空白、引用符の中の `#` を含める

### N-22 コマンドを文に区切る前処理
- 観点: 区切る処理が、引用符の入れ子 (`"$(echo "a && b")"`)、`$'..'`、コメント、`$(...)` と `$((...))`、バッククォート、heredoc 本文の中の引用符、`>|` で、区切りを誤認していないか。読み切れない入力 (閉じていない引用符) で止める側に倒れていないか
- 確かめ方: 上の形を、区切りを含まない 1 コマンドとして「通る」テストにする。区切りの後ろに本物の連結を置いた形も「止まる」テストにする

### N-23 真偽値の設定を複数のファイルで上書きする判定
- 観点: jq の `//` は `false` を「無い」と見るので、後のファイルで `false` に戻した値が前の `true` に負けていないか
- 確かめ方: 前のファイルで `true`、後のファイルで `false` にした入力を試し、後のファイルが優先されるか見る。未設定と `false` を区別するには `select(. != null)` を使う

### N-24 ガードの入力を変形する前処理
- 観点: 入力を変形する前処理 (文字列を空にする、引用符を外す、除く) を足したとき、変形が「検査の対象から外す」方向に働いて、これまで止めていたコマンドを通していないか。除外の条件が、許可リスト (その入力が本当にそれだけか) で書かれているか。拒否リスト (実行系の一覧) は、一覧に無い実行手段 (別のシェル、ssh、parallel、検索ツール自身の実行オプション) で抜ける
- 確かめ方: 変更前の版と同じコマンド集を流して、終了コードが 2 から 0 に変わるものをすべて挙げ、意図した変更かを 1 件ずつ説明する。一覧に無い実行手段を 3 つ以上試す
- 許可リストの中に、オプション名の拒否リストが残っていないか。残るなら、シェルが渡す語 (引用符を外した後。`--p'r'e` は `--pre`) で判定しているか、略称 (`getopt_long` の `--pa`) でも当たるか、許可するオプションを列挙する形にできないかを見る。確かめ方は、引用符で書いたオプション、略称、隣接する引用符を試す

### N-25 標準入力から読むシェルの判定
- 観点: 「引用符の中は実行されない」とみなす規則に、標準入力から読むシェル (`| bash`、`bash <<< ...`、`bash < <(...)`、`| source /dev/stdin`) の例外があるか。その判定が、シェルの前後の形 (オプション、リダイレクト、括弧と `{ }`、`VAR=x`、`env` / `time` / `xargs` / `busybox`、引用符で書いた名前、`$SHELL`、fd 付きの here-string) で外れないか。足す文字列が、実行される範囲 (語の途中だけが引用符の `git" push"` を含む) と一致しているか
- 確かめ方: 上の形を、`echo "git push origin main" | <形>` として止まるテストにする。`-c`、`-n`、スクリプトを渡したシェル、`grep bash` への入力は通るテストにする。判定が正規表現 1 本のときは、シェルの直後に許す文字の集合が狭くないかを見る
